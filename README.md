# VBR REST Job Import / Export

PowerShell helpers that drive the Veeam Backup & Replication (VBR) Configuration Management REST API to migrate a VBR server's configuration — credentials, managed servers, repositories, proxies, and jobs — from one VBR instance to another.

> **Working document, not a production tool.** These scripts were written to test and document the export/import endpoints. Expect to read and edit them before each run.

---

## Limitations

- **VMware backup jobs only.** The underlying REST API does not yet expose every job type; non-VMware jobs are silently dropped.
- **Windows + Git for Windows only.** Scripts shell out to `curl.exe` at the hardcoded path `C:\Program Files\Git\mingw64\bin\curl.exe`. They will not work in PowerShell Core on macOS/Linux without modification.
- **Self-signed certs assumed.** All curl calls use `--insecure`. If your VBR server uses a trusted cert, this is harmless; if it doesn't, you should fix it rather than rely on `--insecure`.
- **Interactive failures.** `JobImport.ps1` pops a `[System.Windows.MessageBox]` on session failure — it expects to run on an interactive Windows desktop, not a headless agent.

---

## Prerequisites

- Windows host with **PowerShell 5.1** (Windows PowerShell, not PowerShell Core).
- **Git for Windows** installed at the default path so `C:\Program Files\Git\mingw64\bin\curl.exe` resolves. If your install differs, edit the `$curlEXE` variable at the top of each script.
- **Network reachability** to both source and target VBR servers on their REST port (default `9419`).
- **Credentials** for the VBR REST API on both servers (built-in `administrator` works in lab environments).
- On the **target** VBR server, the default repository and default proxies should be **deleted before import** so they don't collide with imported objects.

## File layout

| File | Purpose |
| --- | --- |
| `JobExport.ps1` | Calls `/api/v1/automation/{component}/export` on the source server and writes each response to a `*.json` file. |
| `JobImport.ps1` | Reads the `*.json` files and POSTs them to `/api/v1/automation/{component}/import` on the target server, polling each session to completion before moving on. |
| `MigrateJobsToNewServer.ps1` | Work-in-progress consolidation that takes source/target servers as parameters via `Get-Credential`. **Not complete — do not rely on it end-to-end yet.** |
| `.github/workflows/security.yml` | Gitleaks + Semgrep on push/PR/weekly cron. |
| `.gitignore` | Blocks the `*.json` exports from being committed. |

The five JSON files (`CredExport.json`, `JobExport.json`, `managedservers.json`, `proxies.json`, `repos.json`) are **runtime outputs**, not source files. They are generated by `JobExport.ps1` and consumed by `JobImport.ps1`. They must never be committed because they contain credentials and infrastructure details.

## End-to-end migration walkthrough

### 1. Configure the export script

Edit `JobExport.ps1`:

```powershell
$curlEXE       = 'C:\Program Files\Git\mingw64\bin\curl.exe'   # adjust if needed
$serverAddress = "https://<source-vbr-host>:9419"              # source VBR
```

The script's `PostString` and per-component functions also embed the API username and password as `administrator:Veeam123!` in two places (the basic-auth `-u` flag and the OAuth password grant body). Replace those with your source-server credentials before running. **Do not commit your edits.**

### 2. Run the export

By default `JobExport.ps1` only writes `JobExport.json`. To capture every component (you almost always want this), uncomment the remaining `Out-File` lines at the bottom:

```powershell
$jobs       | Out-File JobExport.json
$creds      | Out-File CredExport.json
$mgdServer  | Out-File managedservers.json
GetRepos    | Out-File repos.json
GetProxies  | Out-File proxies.json -Encoding utf8
```

Then run:

```powershell
.\JobExport.ps1
```

Output files land in the repo root in **UTF-16 with BOM** (PowerShell `Out-File` default). The import script depends on this encoding — if you re-encode the files, the inline `-d` body passed to curl will likely break.

### 3. Hand-edit the exported JSON

The REST API will not accept the exports as-is. Three edits are required:

1. **Passwords.** `/credentials/export` returns each credential with an empty `password` field. Open `CredExport.json` and fill in the real password for every credential entry — the API rejects empty strings.
2. **Repository mount hosts.** Each repository in `repos.json` has a `mountServer.mountServerName` that points at the source VBR host. If the target VBR has a different hostname, retarget every entry to a host that exists on the destination side.
3. **Anything else lab-specific.** Cert thumbprints, SSH fingerprints, and IPs are exported verbatim. If the target environment differs, fix them now.

### 4. Configure the import script

Edit `JobImport.ps1`:

```powershell
$curlEXE       = 'C:\Program Files\Git\mingw64\bin\curl.exe'
$serverAddress = "https://<target-vbr-host>:9419"              # target VBR
```

Replace the basic-auth credentials in the curl args (search for `administrator:Veeam123!`) with the target-server credentials.

### 5. Pre-clean the target VBR server

Using the VBR console on the target:

- Delete the **default backup repository** (otherwise the imported repo collides on name).
- Delete the **default proxies** (same reason).

### 6. Run the import

```powershell
.\JobImport.ps1
```

The script imports in this fixed order, polling each session every 5 seconds until it leaves the `Working` state:

1. Credentials
2. Managed servers
3. Repositories
4. Proxies
5. Jobs

If any session reports `result.result == "Failed"`, a Windows message box pops up. The script keeps going to the next stage regardless — read the curl output to see what actually failed.

## Troubleshooting

- **`401 Unauthorized` on every call.** Token expired or basic-auth header is wrong. The token grant uses the OAuth2 password flow against `/api/oauth2/token`; if that returns no `access_token`, every subsequent call will 401. Re-check the `-u` flag and the `-d 'grant_type=password&username=...'` body.
- **`Bad Request` on import.** Almost always means an unedited password field, a stale mount-server name, or a name collision with a default repository/proxy on the target.
- **`x-api-version` mismatch.** The scripts mix `1.0-rev1` (creds, managed servers) and `1.0-rev2` (repos, proxies, jobs). If your target VBR build doesn't accept one of these, bump it — but check the per-endpoint version compatibility, not just the global one.
- **Inline JSON body fails to parse.** The import script does `$x.Replace('"', "'")` to swap double quotes for single quotes before passing the JSON to curl as a `-d` arg. This works *only* because PowerShell `Out-File` writes UTF-16 and the API tolerates single-quoted JSON in this code path. If you regenerate the files with `-Encoding utf8` or reformat them, this trick stops working.

---

## Security

- **Never commit the `*.json` exports** — `.gitignore` blocks them by name. They contain credentials, hostnames, IPs, and cert/SSH fingerprints.
- The repo runs **Gitleaks** and **Semgrep** on every push, PR, and weekly via `.github/workflows/security.yml`.
- Treat any credential that has ever appeared in a JSON export in this repo's history as compromised. Rotate it.
